Flatbed
streamed replies

flatbed · HTTP routes · thufir · design · 2026-11-11 · for flatbed 0.0.13 · for cloud's diadem · every decision ruled · final review applied 2026-11-12 · under #118

A flatbed route answers today with a buffered body: the handler returns a value, the macro serialises it to a Vec<u8>, and hyper sends it as one Full<Bytes>. Cloud's model gateway, diadem, has to forward a provider's server-sent events as they arrive, so its page serves a port from hyper inside a flatbed worker instead of declaring a route. This page proposes the smallest change that lets a route stream: Response::stream beside Response::raw, a body type that is either the bytes or a stream, one wrapper that records how the stream ended, and a request body limit the buffered path has never had. Handlers, the #[route] macro and every existing route keep their shape. Nothing in it is FlatBuffers: a streamed body is whatever bytes the handler hands over, in whatever format the provider spoke.

The question this page answers · 2026-11-11Can a flatbed route answer with a body that streams, so diadem is an ordinary route rather than a hyper listener beside flatbed's, and what else has to move for that to be true: the macro, OpenAPI, the clients, telemetry, timeouts, the sidecar, request bodies, and cloud's pin on 0.0.7?
Final review applied · 2026-11-12

A last review of the design, accepted by the owner (“Apply all”), changed eleven things, each checked against main: a HEAD is stripped on ResponseParts before finish, so Observed never wraps one; the body is UnsyncBoxBody through boxed_unsync everywhere; shutdown pins each connection, calls graceful_shutdown() and awaits it, tracks connection tasks in a JoinSet and flips a shutdown readiness gate; Passthrough is Passthrough(pub Bytes); the handler receives Bytes with no copy; #[nats_route] refuses Passthrough at compile time; TelemetryService gains register_u64_counter_vec; a chunked body over the limit answers 413; the enum is ReplyBody; the rulings are stated as ruled; and Observed's terminal rule is a state machine, End. The six rulings at the foot of the page are kept as the owner ruled them; where an option's text there differs in detail (the content type on Passthrough, a live-connection counter), the sections above are the design.

Timeouts in flatbed1

The graceful-shutdown budget, shutdown_timeout, 30 s by default. No request timeout, no body-read timeout, no compression layer. A long stream has nothing in flatbed to cut it; what could cut it sits in the sidecar.

How a route is built today

Everything below is read from main at 3857442, which is 0.0.12. The HTTP surface is the same shape in the 0.0.7 cloud pins: between the two, hyper/service.rs changed by 83 lines and the macro by 47, none of them the body's type.

The #[route] macro

flatbed_macros/src/lib.rs, route. It takes a path and optional method (default POST), version, tag, summary, operation_id and deprecated. The handler must be async fn(Request<T, Arc<C>>) -> Result<Response<U>, FlatbedRouteError<D>>; the macro reads T, C and U off the signature. It emits a wrapper __hyper_handler_<fn> with the fixed AsyncHandlerFn shape fn(RequestParts, Vec<u8>, &str, Arc<dyn Any>) -> BoxFuture<Result<ResponseParts, Error>>, and an inventory::submit! of a RouteInfo carrying the path, method, type names, the wrapper and an OpenApiRouteInfo. The wrapper decodes the body by the request's content-type: serde_json::from_slice for JSON, T::from_flatbuffer for FlatBuffers, {} for a bodyless method. It downcasts the context, builds the Request, awaits the handler, and turns the result into ResponseParts.

The response type

Response<T> is { body: T, status, headers, raw: Option<(Vec<u8>, Cow<str>)> }. Response::ok, created, accepted, no_content and with_status set body; Response::raw(bytes, content_type) on Response<()> sets raw. In the wrapper, take_raw() wins: raw bytes go out under their own content type; otherwise the body is serde_json::to_vec when the request's accept or content-type asks for JSON, else T::to_flatbuffer(). The result is ResponseParts { body: Vec<u8>, status, headers, content_type } plus x-request-id. build_success_response in hyper/service.rs writes it as Full<Bytes>. Every built-in tier does the same: splash, /healthz, /readyz, /metrics, /openapi.json, /schema.bfbs, static files, 404, 405, 415 and 503.

OpenAPI

Behind the openapi feature, openapi_generation in lib.rs builds the spec from the registered RouteInfos at request time. build_operation gives every route a request body and a 200 response, each with two content entries: application/json referencing the table's component, and application/x-flatbuffers as a binary string whose description carries the .fbs text. The macro fills request_schema and response_schema from <T as ToFlatBuffer>::SCHEMA_FIELDS; () is the table Empty. A Response::raw route is therefore documented as returning Empty in JSON or FlatBuffers, which is not what it sends. Routes group by version under /v{n}/openapi.json.

Middleware, telemetry, request ids

There is no middleware chain on main: FlatbedConfig::before_request is one guard, Fn(&RequestParts) -> Result<(), FlatbedRouteError>, run after routing. The middleware work is issue #50; its first pull request, #77 “Make the HTTP pipeline parts-first”, has been open since 2026-09-05 and makes every tier answer ResponseParts with one finish onto hyper, body still a Vec<u8>. Per-request telemetry is thin: the request id is read from x-request-id or generated and echoed on every reply; a 5xx is logged as route failed and sent to the ErrorReporter with the request id; a handler panic is caught and answered 500 PANIC. No span, no duration, no byte count, no request counter: the TelemetryService has counters with constant labels and labelled gauges, and /metrics serves what the application registered.

Timeouts, body limits, error mapping

No request timeout and no body limit, as the figures above say. The error mapping is in dispatch: a FlatbedRouteError from the handler keeps its status, code and headers; Error::DeserializationError is 400 BAD_REQUEST, SerializationError is 500 SERIALIZATION_ERROR, HandlerError is 500 HANDLER_ERROR, Custom is 500 INTERNAL_ERROR, a body that cannot be read is 400 BODY_READ_ERROR. An error answers in the request's wire format: a JSON body {code, message, details?}, or empty with x-error-code and x-error-message for FlatBuffers. strip_body_for_head collects a reply's body to set content-length on a HEAD, because hyper's HTTP/2 encoder sends a HEAD body it is given.

The clients

clients/ holds one generator, clients/ts/flatbed-client, published as @plonklabs/flatbed-client. It reads /openapi.json and /schema.bfbs. read-openapi.ts keeps an operation only when its request or its success response advertises application/x-flatbuffers; a response without a FlatBuffers entry becomes a method returning Uint8Array. Its transport is fetch followed by res.arrayBuffer(): the whole body, buffered. There is no generated Rust client; a Rust caller uses reqwest, as ingest does. Cloud's website and admin pin ^0.0.3 of the client; flatbed_build's codegen is unchanged between 0.0.7 and 0.0.12.

  1. The caller posts the provider's own JSON to the Service name, over the mesh, with no key. The sidecar stamps x-plonk-caller from the peer certificate and forwards; its route timeout is 0 s, so it will not cut the reply.
  2. The read stays buffered: a streamed request body is a later design.
  3. The body becomes Request<Passthrough> for a route that wants the bytes as sent, the collected Bytes handed over without a copy, or Request<T> as today. The decode moves behind one trait, FromBody, so the macro calls one function instead of inlining the JSON and FlatBuffers branches.
  4. The handler calls the provider with reqwest and gets a reqwest::Response whose bytes_stream() is the body as it arrives. The tee that reads usage is diadem's, wrapped around that stream.
  5. Response::stream(content_type, stream) is the hand-off, a sibling of Response::raw on Response<()>. The handler's signature is the one it has for a raw reply.
  6. The macro's one new branch turns it into ResponseParts { body: ReplyBody::Stream(..) }, adds x-request-id and the handler's headers, and returns.
  7. finish writes it onto hyper as an UnsyncBoxBody, wrapped in Observed, which counts bytes and records how the body ended. Each chunk is pulled only when hyper can send it, so the provider is read no faster than the caller reads.

What streaming touches

The body type

ResponseParts.body becomes an enum, ReplyBody::Full(Vec<u8>) or ReplyBody::Stream(FlatbedBody), named so it does not shadow http_body::Body, with FlatbedBody an UnsyncBoxBody<Bytes, BoxError> from http_body_util and BoxError the usual boxed std::error::Error. Unsync on purpose: hyper-util's serve_connection needs only Send, nothing shares a body across threads, and diadem's usage tee should not have to be Sync; Response::stream bounds its stream Send + 'static and no more. FlatbedService's type Response becomes Response<FlatbedBody>; every built-in tier boxes its Full through BodyExt::boxed_unsync after map_err from Infallible. Response<T> and ResponseParts derive Debug and a stream has none, so ReplyBody writes its own, printing Stream(..). Full stays the fast path: a buffered reply is boxed once at finish and nothing else about it changes.

// crates/flatbed/src/lib.rs
pub type BoxError = Box<dyn std::error::Error + Send + Sync>;
pub type FlatbedBody = UnsyncBoxBody<Bytes, BoxError>;

pub enum ReplyBody { Full(Vec<u8>), Stream(FlatbedBody) }   // Debug by hand: Stream(..)

impl Response<()> {
    pub fn raw(bytes: impl Into<Vec<u8>>, content_type: impl Into<Cow<'static, str>>) -> Self;
    pub fn stream<S, E>(content_type: impl Into<Cow<'static, str>>, stream: S) -> Self
    where
        S: Stream<Item = Result<Bytes, E>> + Send + 'static,
        E: Into<BoxError>;
}

pub struct Passthrough(pub Bytes);
pub type AsyncHandlerFn = fn(RequestParts, Bytes, &str, Arc<dyn Any + Send + Sync>) -> BoxFuture<..>;   // was Vec<u8>

// crates/flatbed/src/hyper/service.rs
impl<C> Service<Request<Incoming>> for FlatbedService<C> {
    type Response = Response<FlatbedBody>;   // was Response<Full<Bytes>>
}

The macro and the handler signature

Unchanged for every route that exists. Response::stream stores its stream where raw stores its bytes; take_raw() becomes take_body() returning Option<(ReplyBody, Cow<str>)>, and the wrapper's if let Some((bytes, content_type)) = response.take_raw() gains a second arm that builds ResponseParts with ReplyBody::Stream. futures is a dependency in every build since 0.0.11, so Stream is already there; http_body_util::StreamBody maps each Bytes to a data frame. A route that streams is written like a raw route:

#[route("/v1/responses", produces = "text/event-stream, application/json")]
async fn responses(req: Request<Passthrough, Arc<Ctx>>) -> Result<Response<()>, FlatbedRouteError> {
    let upstream = req.ctx.forward(&req).await?;        // reqwest::Response, headers in hand
    let content_type = upstream.content_type().to_owned();
    let usage = req.ctx.usage_reader(&upstream);
    let body = upstream.bytes_stream().inspect_ok(move |chunk| usage.feed(chunk));
    Ok(Response::stream(content_type, body).status(upstream.status()))
}

OpenAPI

The spec is built from static route data, so the media type cannot be derived from a runtime Response::stream call; it is declared. A new attribute, produces = "…", a comma-separated list of media types, replaces the JSON and FlatBuffers response entries with one entry per type: an opaque string of format: binary for anything that is not application/json, and for application/json an opaque {} schema with no $ref, since the route's JSON is whatever it forwards. A streamed text/event-stream is documented as such; a diadem route that answers SSE or JSON by the request's stream field lists both. The same attribute lets a Response::raw route stop being documented as returning Empty, but it stays optional there: a raw route that computes its content type per request, as cloud's integrations/src/routes/design.rs does, is not made to declare one. The request side is untouched, except that Request<Passthrough> is documented as a request body with no schema under the content types the route accepts.

The clients

Server-side and opt-in. A route with produces and no application/x-flatbuffers response is already an operation read-openapi.ts would emit as Uint8Array, buffered by res.arrayBuffer(), which would read a stream to its end before returning: wrong for SSE and silently so. The generator therefore skips any operation whose success response lists a media type that is neither JSON nor FlatBuffers, and says so in its output; the example route above, with text/event-stream, application/json, is skipped by that rule, where a rule reading only "no JSON entry" would have emitted it and buffered the SSE. No SSE parser, no ReadableStream method: diadem's callers are pi, through its own OpenAI client, and ingest, through reqwest; neither is a generated client. Nothing changes for cloud's website and admin, whose generated clients call no such route.

Telemetry at the end of the body

The handler has returned by the time the first byte goes out, so a streamed reply is observed by a wrapper body, Observed, applied at finish only to ReplyBody::Stream. It carries the route, path, request id and the status already sent, a start Instant and a byte count. It emits exactly one terminal event per body, the first of end, error or drop, through a small state machine, enum End { Open, Completed, Failed, Disconnected }: the body starts Open, only the move out of Open emits, and every later move is a no-op, so a stream that errs and is then dropped is recorded once. End is a plain type with no hyper in it, unit-tested on its own. On the stream's end it logs stream ended at info with outcome=completed, bytes and duration. If it is dropped before the end, which is how hyper tells it the connection went away, Drop logs outcome=disconnected with the bytes so far. An Err from the stream is reported to the ErrorReporter through route_error as a RouteFailure whose request is the HTTP transport, method, route, path and request id, whose status is the one already sent (200, not 500), whose code is STREAM_ERROR and whose message is the error's Display; it is logged outcome=failed, and then the transfer is aborted (ruling 1): HTTP/1.1 closes the connection without the final chunk, HTTP/2 resets the stream. The status cannot change: it was sent with the headers. A provider-shaped error event inside the body, such as an SSE error frame, is a choice diadem makes inside its stream, not something flatbed writes. Counters per route and outcome are left out of flatbed: the log line is what the stream needs, and the labelled counter diadem keeps per namespace and per alias goes through register_u64_counter_vec, below.

Backpressure and disconnects

Hyper polls a response body only when the connection has room to send: HTTP/2 flow-control window, or a writable HTTP/1.1 socket. The stream is polled on demand, so the reqwest body behind it is read at the caller's pace and the provider sees the same backpressure. When the caller closes its connection, hyper drops the response body; dropping Observed drops the StreamBody, which drops the handler's stream, which drops the reqwest::Response, which closes or resets the upstream connection. That chain is the contract: cancellation by drop. The upstream call is owned by the stream the handler returns, never by a task flatbed spawns; a handler that wants an upstream to outlive its caller spawns that itself and hands flatbed a channel. The test in the table below asserts the drop reaches the upstream.

Timeouts that would cut a long stream

In flatbed, none: no request timeout exists, and the only budget is shutdown. In the mesh, the inbound a caller_identity box opts into is an HTTP connection manager, and plonk's operator sets its route timeout to 0 s and stream_idle_timeout to 3600 s (xds/caller_identity.rs, STREAM_IDLE_TIMEOUT_SECS), because Envoy's default 15 s route timeout would cut every long reply. A box without caller_identity sits behind a TCP proxy with no HTTP timeouts at all, and the outbound leg of every box is a TCP proxy too (xds/listeners.rs). So a stream from diadem crosses one HTTP-aware hop, already configured, and that configuration is plonk's to keep, not flatbed's. A stream quiet for an hour is cut by the sidecar; a model that says nothing for an hour has failed anyway.

Request bodies: the limit

The buffered path gets the limit it has never had, in two places: a service-wide default, FlatbedConfig::max_request_body(bytes), and a per-route override, #[route(…, max_body = 25 * 1024 * 1024)], carried on RouteInfo. dispatch checks content-length against the route's limit before reading a byte, and counts bytes during the collect for a chunked request with no length, through http_body_util::Limited, whose collect then fails with a boxed LengthLimitError; dispatch checks it with downcast_ref to answer 413, and only another read error stays 400 BODY_READ_ERROR. An oversized request is answered through the route-error path, 413 PAYLOAD_TOO_LARGE with x-request-id and the request's wire format, like every error after routing since 0.0.11. max_body takes an expression, not only a literal, emitted into a const the compiler evaluates, so 25 * 1024 * 1024 is accepted. An early 413 leaves the request body unread, and on HTTP/1.1 hyper then closes the connection; a client still sending may read a reset instead of the status. There is no reset-free answer short of consuming a body that is by definition over the limit, so the page recommends documenting it: the 413 is a defence, and a client that wants it reliably sends Expect: 100-continue, which hyper honours by sending 100 Continue only when the body is first polled, so the early answer reaches it before a body byte leaves. The test below sends 7 MB both ways and records what a client without Expect reads. There is no limit today, so any default changes behaviour; it is listed as breaking, and ruling 3 sets it at 16 MiB. A streamed request body, read chunk by chunk and never collected, stays a separate, later design, with its own extractor; what would trigger it is a caller sending past 20 MB, or whole files.

Request bodies: what diadem receives

Measured in cloud's ingest. Video is never uploaded: Vertex reads it as a gs:// fileData reference (vertex.rs), so the request is small. Keyframes to OpenRouter vision: up to 10 JPEGs per call (FRAMES_PER_CALL = 10, describe.rs), inline as base64 data URLs (chat.rs), about 1 to 4 MB a request. Audio, to OpenRouter as input_audio and to Vertex as inlineData: mp3 at 16 kHz mono, 64 kbps (ffmpeg.rs), in chunks of up to 10 minutes (CHUNKS, transcribe.rs), about 4.8 MB raw and 6.4 MB as base64; the explicit tier cuts 3-minute chunks, 1.4 MB. Ingest's own comment: a request carries at most 20 MB inline. An image is one JPEG inline. So bodies reach about 7 MB and are bounded at 20 MB by the providers; diadem's routes set max_body around 25 MB.

Memory and the sidecar

Memory: bodies are held whole, and diadem parses the JSON to rewrite model, so the bound is the largest body times concurrent requests, twice over while the parse holds both. Forwarding the bytes as received avoids a base64 decode, which would double it again. Diadem runs one replica; ingest's boxes are single replicas sending one call at a time, and pi sends one turn per active creator, so a handful of bodies in flight is the expected shape. Diadem's page gives no memory limit, so a PlonkBox's default 256Mi would apply; at 25 MB a body that holds about four parses beside the process, and the page should set memory_limit from the ingest box count. The sidecar: Envoy caps no request size unless a buffer filter is present, and none is in this path; its default 15 s route timeout would also cut a slow upload, which is one more reason the caller_identity inbound's timeout: 0 s matters.

Compression and buffering

Flatbed has no compression layer, so nothing in it buffers SSE. Envoy's compressor and buffer filters would, and plonk's xDS configures neither on any listener. The rule that keeps streams working is therefore a rule on plonk's mesh: no compressor or buffer filter on a caller_identity inbound. Flatbed documents in its README that a streamed reply is sent uncompressed and that a proxy in front must not buffer it.

Middleware, as #77 shapes it

#77 makes every tier answer ResponseParts and funnels them through one finish; this design puts ReplyBody into that struct and Observed into that function, so the two compose rather than collide, and #77 rebased onto 0.0.13 changes one field type. What a middleware can do with a streamed reply is bounded by the shape: it can read and change the status and headers, because they exist before the body starts, and it can wrap the body in another body. It cannot read or rewrite the body's bytes, because they have not arrived; a middleware that needs the whole body sees a ReplyBody::Stream and must pass it through. The middleware design should say that in its own words when it lands.

HEAD

Today handle_request runs dispatch, which has already built the hyper response through build_success_response, and only then calls strip_body_for_head, which collects the reply to set content-length. A streamed reply must not be collected, since collecting it would read the provider to the end; and it must not be stripped there either, because by then finish has wrapped it in Observed, and dropping it would log a false disconnected. So a HEAD is stripped on ResponseParts, before finish, at the seam between respond and finish that #77 introduces: a Full body's length becomes content-length and the body empties; a ReplyBody::Stream is dropped without being polled and no content-length is set. Observed never wraps a HEAD reply. The existing h2c test, test_head_request_builtins_strip_body_keep_length, stays the receipt for buffered replies; a sibling asserts the streaming case polls nothing and logs no stream ended.

Shutdown

Today AutoServer::serve selects each connection against the shutdown signal: on SIGTERM every in-flight connection future is dropped at once, buffered or not, and the process waits for the worker drains and a 2 s epilogue, or the whole 30 s budget when there are no drains. A long stream is cut at the first instant of every rollout. Ruling 2 holds in-flight bodies up to shutdown_timeout, which is three changes in serve. Readiness: serve registers a gate on the service's Readiness at start, config.readiness.gate("shutdown"), and sets it ready; the signal task calls ReadinessGate::set_ready(false) on it first, so /readyz answers 503 Not Ready: shutdown before the drains and the sidecar and Kubernetes stop sending. Since dispatch answers every route 503 NOT_READY while a gate is down, a new request that still reaches an open connection is refused, not started. The connection: each task pins it, let mut conn = pin!(builder.serve_connection(io, service)), and on the signal calls conn.as_mut().graceful_shutdown() and then conn.await, where today's select! arm (server.rs, lines 165 to 175) drops it. The wait: connection tasks are spawned into a JoinSet, reaped by join_next in the accept loop so finished ones do not pile up, and after the loop the set is awaited under tokio::time::timeout for shutdown_timeout, beside the worker drains, replacing the fixed sleep; dropping the set past the budget aborts what is left. No counter is kept.

Request<Passthrough>

Passthrough(pub Bytes) is the body exactly as sent and nothing else: the 415 rule has already parsed the content type into the codec, and a pass-through forwards the request's headers anyway. The handler receives Bytes: AsyncHandlerFn takes Bytes where it took Vec<u8>, and dispatch drops the collected.to_bytes().to_vec() copy (service.rs, line 313), so a 25 MB body reaches the handler with no copy after hyper's collect; the JSON and FlatBuffers decodes read the same slice. That is a breaking change to a public type, felt only by code that names AsyncHandlerFn, which the macro writes. #[nats_route] does not take FromBody: its wrapper inlines its own JSON and FlatBuffers decode, and keeps it. Passthrough implements neither, so it can never compile there, and the macro names why with a compile error when the body type is Passthrough, the way the runtime answers a NATS Response::stream with STREAM_NOT_SUPPORTED; a unit test beside the macro's others holds it. That is smaller than threading FromBody through the NATS wrapper to raise a PASSTHROUGH_NOT_SUPPORTED reply at run time.

A labelled counter

Diadem counts per namespace and per alias, the TelemetryService's registry is private, and cloud takes one flatbed bump, not two. So TelemetryService gains register_u64_counter_vec(name, help, label_names), the counter twin of register_u64_gauge_vec: a default Err so a counter-only backend still compiles, a CounterVec<u64> trait beside GaugeVec whose inc_by(label_values, value) logs and skips an arity mismatch, and a Prometheus impl over IntCounterVec with the service's constant labels. One test registers it, increments two label tuples and reads both series from the feed. flatbed itself registers no per-route counter.

Worked examples: diadem's three calls

pi · POST /v1/responses · stream: true

The route above. Request<Passthrough> gives diadem the body as pi sent it; it rewrites model, adds the key, posts to OpenAI, and hands the bytes_stream() to Response::stream under OpenAI's own content type, status copied. The tee reads response.completed as it passes. The sidecar's route timeout is 0 s, so a deep turn of several minutes is not cut; Observed logs the end with the byte count. An abandoned turn: diadem stops when the client hangs up and records the row as abandoned, with tokens unknown; there is no drain task. Flatbed's cancellation by drop is exactly that: pi closing the connection drops the stream, which drops the OpenAI call before response.completed, and the tee sees the stream end without usage.

ingest · Vertex generateContent · unstreamed

The model sits in the path, /v1/…/models/{alias}:generateContent, which the router already extracts as a path parameter. The body, up to 6.4 MB of base64 audio for transcription, is read under the limit and handed over as Passthrough. Vertex answers one JSON document, and the caller did not ask for a stream, so the reply is buffered: Response::raw(bytes, content_type) after reading the body to the end, as the route does today. One route, two hand-offs: raw when the caller did not ask for a stream, stream when it did.

ingest · OpenRouter /audio/transcriptions · unstreamed

A JSON body of about 1.9 MB with the mp3 as base64 input_audio, inside OpenRouter's 60 s. Buffered both ways, like the Vertex call, since the reply is not streamed: Response::raw. Nothing streams here; what this call needs from the design is only the request limit's default clearing 2 MB, which ruling 3's 16 MiB covers with a wide margin.

Existing routes, the version, and cloud's bump

What changes for an existing route

In source, nothing: the signature, the macro attributes and Response::ok are what they were. On the wire, one thing: a request over max_request_body's default is 413 where it was read whole before. That is the one breaking change an existing route can feel, and ruling 3 sets it at 16 MiB. Cloud's own caps are far below it: mail's push route refuses over 64 KiB and auth's tap over 4 KiB, both by hand, and diadem's 7 MB bodies sit under it.

The version, and whether it breaks

0.0.13 at the earliest, and yes, it is a breaking change, which a 0.0.x bump is allowed to be: FlatbedService's public Response type moves from Full<Bytes> to FlatbedBody, ResponseParts.body moves from Vec<u8> to ReplyBody, AsyncHandlerFn takes Bytes where it took Vec<u8>, the doc-hidden take_raw becomes take_body, and max_request_body has a default where no limit existed. The type changes break anyone driving FlatbedService, AutoServer or ServiceContext directly; cloud names none of them. The changelog entries go under Changed as BREAKING, beside Added for Response::stream, Passthrough, produces, max_request_body, max_body and register_u64_counter_vec.

What cloud absorbs from 0.0.8 to 0.0.12

Read from CHANGELOG.md and checked against cloud's source. Cloud's five services call Flatbed::run from their own #[tokio::main], implement Worker at 31 sites, construct no WorkerInfo, use no LocalQueueWorker, and run Rust 1.99 under mise. Decisions, ruled by the owner · 2026-11-11

Each box keeps the options as they were put, and carries the owner's words. The flatbed maintainer had agreed with the six recommendations; the owner has now ruled every one.

ruled 1 · what the caller sees when the stream fails mid-way

Ruled: A, abort the transfer. The owner: “yes”.

The status is on the wire; only the transfer can say something went wrong.

A. Abort the transfer. Observed passes the Err to hyper: HTTP/1.1 closes the connection without the final chunk, HTTP/2 resets the stream. A client library reports an incomplete body; pi's SSE reader sees a network error and can retry or fail its turn. Costs: an abrupt close in the sidecar's access log.

B. End the body cleanly. The error is logged and reported, and the body ends as if complete. Costs: a truncated reply looks finished; an SSE consumer waits for a response.completed that never comes, until its own idle timeout.

Recommendation: A. The pass-through was chosen for fidelity; a reply that was cut must look cut.

ruled 2 · a long stream at shutdown

Ruled: B, hold in-flight bodies up to shutdown_timeout. The owner: “yes”.

A. Keep cutting. Today's select! drops every in-flight connection at SIGTERM; a stream dies at the first instant of each rollout, and so does any buffered reply still being written. Costs: nothing to build; one failed turn per pi conversation open during a diadem deploy.

B. Hold up to the budget. On SIGTERM, /readyz goes to 503 before the drains; each connection's pinned auto::Connection is told graceful_shutdown() and awaited rather than dropped, so no new requests start on it and in-flight replies finish; the fixed sleep after the drains becomes a wait on a count of live connections, bounded by shutdown_timeout, after which what is left is cut. Costs: a connection counter the server has not kept and a readiness flip at shutdown; the pod's termination grace period must be at least the budget, which is a check on the PlonkBox side; a stream longer than the budget is still cut.

Recommendation: B. It fixes the buffered case too, and diadem can set its budget to the longest turn it wants to protect.

ruled 3 · the request body limit's default

Ruled: A, 16 MiB. The owner first asked “idk videos can be very heavy... are you sure?”, and after the explanation below, “yes to both”. Why a video never meets the buffered limit in cloud: a safe video goes to Vertex as a gs:// URI (ingest/src/roles/media_analyzer.rs, file()), and an explicit video goes to OpenRouter as at most 10 keyframes per request, each downscaled to 1024 px (frames(), MODERATE_SIDE). A real video upload, if cloud ever takes one, streams to storage and never raises this limit.

There is no limit today, so either default is a breaking change, and the choice is how generous to be so that no existing service breaks. Diadem does not depend on it: its routes set max_body at about 25 MB.

A. 16 MiB. Over twice the largest body cloud sends, 7 MB, and far over mail's and auth's hand-made caps. Costs: a service outside cloud posting between 16 and 32 MiB would start seeing 413; none is known.

B. 32 MiB. More room for a service nobody has measured. Costs: twice the memory an unmeasured service can be made to hold per request, which is what the limit exists to bound.

Recommendation: A. The known bodies fit with room, a service that needs more names it on the config or the route, and the smaller ceiling is the point of having one.

ruled 4 · how the spec learns the media type

Ruled: A, the produces attribute. The owner: “sure”.

A. produces = "…" on the route. Static, a list, documents raw routes honestly too, and the wire type stays the runtime argument of Response::stream and Response::raw, which is what a pass-through needs since it answers whatever the provider answered. Costs: a route can declare one thing and send another; nothing checks it.

B. Derived from the call. Not possible: the spec is built from the registry before any handler has run, and a handler's content type is a value it computes per request.

Recommendation: A.

ruled 5 · the TypeScript client on a streaming route

Ruled: A, skip them. The owner: “yes, skip them we don't need them or when we have them we will do them with flatbuffers for the TS client”.

A. Skip it: any operation whose success response lists a media type that is neither JSON nor FlatBuffers, with a line in the generator's output naming it. Costs: a TypeScript caller of such a route writes its own fetch.

B. Emit a method returning the Response or its ReadableStream. Costs: a second transport shape beside FlatbedResponse, which today is status, headers, body: Uint8Array, and a method that no cloud client calls.

Recommendation: A. Server-side and opt-in; the client follows when a TypeScript caller exists.

ruled 6 · how a route receives an arbitrary body

Ruled: B, in flatbed, and the type is named for what it does: Request<Passthrough>. The owner: “raw request beucase its fforwarding... maybe the macro should be name indicating that”, and on the options, “yes to both”. No new macro: the type name says the body is forwarded untouched. A passthrough route flag that lifts the 415 rule stays a possible later change, if non-JSON forwarding is ever needed.

A. In diadem, with no flatbed change. A newtype over serde_json::Value implementing ToFlatBuffer and FromFlatBuffer by hand, with empty schema fields. Costs: the body is parsed and re-serialised, so it is the same JSON but not the same bytes, and the spec documents the request as the table Empty.

B. Request<Passthrough> in flatbed, behind a FromBody trait the macro calls once; Passthrough keeps the bytes and the content type, and the 415 rule still applies: JSON or FlatBuffers in, so diadem's routes accept JSON only and a multipart caller gets a 415. Costs: the macro's decode block moves behind a trait, which is a change every route compiles through; it is also the seam the later streamed request body plugs into.

Recommendation: B. “Forwarded byte for byte” is a claim diadem's page makes; only B keeps it true.
