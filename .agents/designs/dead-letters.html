Dead letters
for the queue

flatbed · local queue · thufir · proposal · 2026-11-03 · for flatbed 0.0.11 · under plonk#6829

A message that keeps failing, or runs too long, is set aside and the line moves on. flatbed 0.0.10's LocalQueueWorker handles one message at a time and has no way to give up on one: a Retry goes back in line forever, a slow handle holds every message behind it, and an Err is dropped with only a log line. 0.0.11 adds a limit on attempts, a limit on time, and a dead-letter set the worker hands a message to when either runs out. The worker decides what setting it aside means, and a producer can see that it was.

Why now

Longest one migration can hold the line2h

plonk#6829's Migrate handler waits for its Job to end, and the migrator's Job carries activeDeadlineSeconds: 7200. A pod stuck on an image pull holds every PlonkRDS change in the cluster for that long.

Times a Retry is tried before giving up∞

handle_messages in local_queue.rs puts a Retry back at the end of the line every time. A message that can never succeed costs one RETRY_DELAY per lap, for good.

Record an Err leaves1 log

An Err from handle is logged at error and dropped. Nothing a producer can read says it happened, so a level-triggered producer sends it again on its next pass.

Fig. 1Where a message can end, before and after

Every outcome that is not Done now has an end: a retry until the attempts run out, a handle until the time runs out, and an Err at once. Each goes through the worker's dead_letter hook, inside the line, before the next message is taken.

Today's queue New in 0.0.11 A message moving A new path A producer reading
  1. The line hands out the next message. As today, next() takes the front entry and marks its key in hand.
  2. handle runs, now under a clock and a panic guard. With HANDLE_TIMEOUT set, the future is dropped when it runs out, as a leadership loss drops it today. A panic is caught and becomes Failed("panicked: …"), instead of taking the worker down and losing the message.
  3. Done ends it and clears its count. Unchanged.
  4. Retry counts an attempt. Under MAX_ATTEMPTS it goes back in line as today; at the limit it is set aside instead.
  5. A time-out, the last attempt, an Err or a panic calls dead_letter. A time-out goes straight there, without another attempt. The worker's hook gets the message and why, and the line waits for it, under the same HANDLE_TIMEOUT, so a hook that hangs can't wedge the line either. The operator uses that wait to delete a Job before the next change starts. The hook is best effort: a leadership loss cancels it, so a handler also clears what an earlier term left, such as a stale Job, at the start of its next attempt.
  6. The message joins the dead-letter set. It is kept by key beside the queue, in memory, and cleared with it on a leadership loss.
  7. Producers can see it and bring it back. status reports it, a send of that key is refused so a producer's next pass does not loop it straight back, and requeue puts it at the end of the line with its attempts reset. flatbed can't tell a changed payload from the same one, since a message has no Eq, so bringing a key back when its spec changes is the producer's rule: it compares the generation it last sent and calls requeue.

What it reads

From the worker, as constants
  • MAX_ATTEMPTS: Option<NonZeroU32>, None by default: how many times handle may run for one key before it is set aside. A Retry is an attempt; a resend coalesced into a queued key keeps its count; Done clears it.
  • HANDLE_TIMEOUT: Option<Duration>, None by default: longest one handle may run.
  • DEAD_LETTER_CAPACITY: usize, 256 by default: most messages kept aside. Past it the oldest is evicted, logged at warn, and its key can be sent again.
From each attempt
  • The LocalQueueResult or Err that handle returned, or that the clock ran out first
  • The attempt count kept for the key in hand
  • The reason a Retry or Err carried, kept as the last reason

The API, as proposed

pub trait LocalQueueWorker {
    // ... as in 0.0.10 ...
    const MAX_ATTEMPTS: Option<NonZeroU32> = None;
    const HANDLE_TIMEOUT: Option<Duration> = None;   // bounds handle and dead_letter
    const DEAD_LETTER_CAPACITY: usize = 256;

    /// Runs in the line: the next message waits for it. Best effort:
    /// a leadership loss cancels it, as it cancels handle.
    fn dead_letter(&self, ctx: Arc<Self::Context>, msg: Self::Message, letter: DeadLetter)
        -> BoxFuture<()> { /* default: log at error */ }
}

#[derive(Clone)]
pub struct DeadLetter { pub cause: DeadLetterCause, pub attempts: u32,
                        pub last_reason: Option<String>, pub at: SystemTime }
#[derive(Clone)]
pub enum DeadLetterCause { Exhausted, TimedOut { after: Duration }, Failed(String) }  // a panic is Failed

#[non_exhaustive]
pub enum SendError { Full(LocalQueueFull), DeadLettered }

impl<W> LocalQueueSender<W> {
    pub fn send(&self, msg: W::Message) -> Result<(), SendError>;
    pub fn status(&self, key: &W::Key) -> KeyStatus;   // replaces position:
                                                       // InHand | Queued(n) | DeadLettered(DeadLetter) | Absent
    pub fn requeue(&self, key: &W::Key) -> Result<(), LocalQueueFull>;
    pub fn forget(&self, key: &W::Key) -> bool;
}

The key's bounds don't change: Key needs no Clone, because there is no call that lists every set-aside key. A producer knows its own keys and asks status for each. With the constants at their defaults there is no limit on attempts or time. Three things change for every caller: send's error type, status in place of position, and what an Err does (decision 1).

Decisions, ruled 2026-11-03

The owner, 2026-11-03yes, the dead letters artifact looks good, also put it on main. And I can rule positive for both points

The owner approved the page as proposed: every decision below is ruled its proposal.

1. An Err always sets the key aside

ruled 2026-11-03 Proposed, and the flatbed session's lean too: yes, in every worker, as 0.0.11's stated breaking change. An Err means the message is bad, and dropping it silently was the weak spot. The cost: a producer that counted on "Err, then the next pass resends" now has its key refused until it calls requeue. Alternative: the set is used only by a worker that sets MAX_ATTEMPTS or HANDLE_TIMEOUT, and an Err elsewhere is logged and dropped as today. Nothing changes for workers that don't opt in.

A resend of a set-aside key is an error

Settled with the flatbed session: send returns Err(SendError::DeadLettered), not Ok with an outcome, because an outcome is too easy to drop with let _ =. A producer brings a key back with requeue.

2. The hook runs inside the line

ruled 2026-11-03 Proposed, and agreed by the flatbed session: the next message waits for dead_letter to return, under HANDLE_TIMEOUT, so cleaning up after a timed-out handle, like deleting its Job, finishes before anything else starts. A leadership loss cancels the hook as it cancels handle, so the hook is best effort and handlers clear stale work themselves. Alternative: the hook runs beside the line. The line moves faster, but the cleanup can overlap the next message, which for #6829 is the collision the queue exists to stop.

3. A Retry counts as an attempt

ruled 2026-11-03 Proposed: yes, so a message that can never be ready is set aside too. The cost: while a server is down for a long time, its messages are set aside rather than waiting, and come back by requeue when it's up. Alternative: only Err and time-outs count, and a Retry loops as today. #6829 would then set a cap on its own retries.

4. The limits #6829 sets

ruled 2026-11-03 Proposed: HANDLE_TIMEOUT of 15 minutes, well above a migration's few statements and a Job's start-up, and MAX_ATTEMPTS of 5, matching the five retries ruled for plonk_migrate. Alternative: other numbers; a timed run of a migrator Job on omega would ground the first, and it isn't measured yet.
